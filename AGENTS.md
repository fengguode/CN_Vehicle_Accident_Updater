# Codex project guidance

This is the broad China traffic incident updater and application. Reports need not mention ADAS; retain ADAS details when present. Preserve source URLs, raw-record provenance, and the distinction between unverified leads and verified incidents. Use isolated services and disposable databases for tests that change accounts or reports.

## Canonical backlog

Track all project tasks, decisions, findings, and follow-ups in the shared [`docs/PROJECT_BACKLOG.md`](docs/PROJECT_BACKLOG.md), including work in sibling variants. Maintain stable IDs, an owner, one status (`Not started`, `In progress`, `Blocked`, or `Complete`), updated date, scope, dependencies/blockers, acceptance criteria/evidence, related QA/review/roundtable links, and Git state for every affected repository. Update the backlog as work starts, ownership or status changes, new tester findings arrive, blockers change, and items complete. The primary agent owns integration and closure; tester findings remain open until the fix is independently retested. Never mark complete without required QA/review and Git evidence. This is the single project-level status source; detailed QA and design notes remain linked evidence.

Read this repository's README for behavior and commands relevant to the task. The primary agent owns each authorized task through implementation, QA, review, and a concise handoff. Define observable acceptance checks before implementation. Every change requires a recorded QA session before it can be marked complete. Record the changed files, environment, acceptance checks, scenarios and actual results, evidence, findings/disposition, and limitations in the task conversation or a task-specific QA note. Scale doc-only checks proportionally, but still record them. A failed or unavailable required check leaves the task incomplete/blocked; report the exact blocker. Make a short plan for substantial changes; keep small fixes lightweight. Delegate independent, bounded work only when it can proceed alongside useful primary-agent work. Give each subagent a scope, file ownership, and expected evidence.

Use the project roles in `.codex/agents/`: `controller` for cost/value and effectiveness reviews, `qualitymanager` for workflow, QA, and traceability audits, `explorer` for read-only codebase and evidence investigation, `system_architect` for stakeholder-led requirements and architecture decisions, `ui_designer` for complete interface and interaction design, `worker` for bounded implementation, `reviewer` for independent code review, and `user_tester` for project-wide test management. The System Architect traces requirements to owner/designer/user evidence and resolves material design gaps before dependent implementation. The Controller reports measured costs or explicitly labeled estimates and does not waive quality gates. For UI work, obtain design criteria before implementation and require a User Tester pass after a runnable version exists. For security, authentication, account, and data flows, run integration checks against isolated services/accounts/databases, never live resources. Avoid overlapping edits. The primary agent fixes findings, verifies the integrated result, and owns the completion decision. Follow the workspace QA gate in `../docs/CODEX_WORKFLOW.md` when working from the umbrella workspace.

Run the narrowest meaningful checks and report only checks that actually ran. Use `npm test` when relevant to code changes and available here. Use disposable data for mutating tests. Preserve existing user changes. Treat publication, live-service changes, Windows scheduled tasks, and real-account or production-data changes as separate operational actions that require task authorization.
