The harness calculation uses CSS computed foreground/background colors and nearest opaque ancestor background. It does not composite translucent ancestor layers or each control's opacity. For disabled Previous, the primary separately composited the recorded CSS border/fill over its recorded adjacent background using opacity 0.45; the resulting ~1.65:1 boundary is an estimate, not pixel-captured output. W3C's [WCAG 2.2 SC 1.4.11 Understanding document](https://www.w3.org/WAI/WCAG22/understanding/non-text-contrast.html) explicitly excludes inactive controls such as disabled HTML controls from the 3:1 contrast requirement. The disabled button result is therefore recorded as a usability observation, not a WCAG defect. Native select arrows, antialiasing, browser pixel compositing, device scaling, hover/focus states, and forced-colors rendering were not measured. A computed border color with `borderWidth: 0px` is not evidence of a visible boundary. These values support only ordinary field borders and enabled button fills explicitly identified above, not a site-wide or device-rendered contrast certification.

Dennis's independent read-only review confirmed the ordinary input-field and enabled-button CSS comparisons are internally consistent, but withdrew the zero-width disclosure-border claim and requested opacity-aware treatment for disabled Previous. The primary recorded the explicit opacity-composited CSS estimate above. Neither issue establishes a product defect. The raw computed values remain in `results.json` with explicit review dispositions so they are not mistaken for valid boundary measurements.
